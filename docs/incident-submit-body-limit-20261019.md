# 事故记录：`/api/run/submit` 请求体超限导致高分成绩丢失（2026-10-19）

## 一句话

DoS 加固时给 `/api/run/submit` 单独设了 `client_max_body_size 64k`，但提交包里带**完整 trace**
（每次投放一条，约 32 字节），长度随对局线性增长。结果：**trace 超过 64KB 的长局（也就是分最高那批）
全部提交失败，nginx 直接 413，成绩丢失且没有任何重试。**

## 现场

玩家「玩家F」打了一局无尽 **13527 分 / 2507 合成 / 8635 秒（2.4 小时）**，本可上到无尽榜第 2 名。

```
nginx 访问日志：
  23:28:17  413  /api/run/submit  111.205.232.xxx
  23:29:00  413  /api/run/submit  111.205.232.xxx
  23:29:35  413  /api/run/submit  111.205.232.xxx
  23:30:30  413  /api/run/submit  111.205.232.xxx
```

> IP 末位已做脱敏处理。

请求体实测 **79.1 KB**（2553 条 trace，平均 32 字节/条）。库里 trace 最大的几局：
18454 分 = 98.3KB、12319 分 = 79.5KB、9443 分 = 57.8KB —— **凡是接近或超过 64KB 的都交不上**。

客户端表现：结果页显示「已记入本机，暂未进入在线榜单」，然后**不再重试**。玩家只能看着成绩没了。
`live_game` 里那行 `result` 永远是 `null`，随后被下一局顶成 `abandoned=1`。

## 修复

```nginx
location = /api/run/submit {
    client_max_body_size 1m;    # 原来是 64k
    ...
}
```

- 1m 与 `/api/` 保持一致，也与后端 `MAX_BODY = 1MB` 一致
- trace 上限 20000 条 ≈ 640KB，1m 有 1.6 倍余量
- 现场修法：`deploy/scripts/fix-submit-body-limit.mjs`（备份 → 只改 submit 块 → `nginx -t` → reload）
- 生产已生效（`.bak-20261019153837`），`nginx -t` 通过

## 抢救

`live_game` 里那行的完整 state 还在（status=over，物理推演抽样 200 次、累计偏差 +1，4σ 界 50.9），
所以能原样救回来：`tools/recover-run-13527.mjs`

复核结果：`validateRun` 无 flags、分数曲线正常、落点 651 种 / 跨度 941px（2553 次投放，上限 100）。
写入后无尽榜第 2 名：`18454 玩家B / 13527 玩家F / 12319 玩家G`。

## 教训

1. **限制请求体大小时必须先看包里最长的字段随什么增长。** trace 随对局长度线性增长，
   而"分最高的局"恰好是最长的局 —— 这条限制精确地打击了最该保护的用户。
2. **改动要在真机数据上验一遍**：库里本来就有 98KB 的 trace（18454 那局），一眼就能发现 64k 不够。
3. 提交失败**不能静默**。目前客户端只在结果页提示一句，没有重试；
   `live_game` 里 `status='over' AND result IS NULL` 是"已打完但没交上"的完整名单
   （`tools/scan-lost-runs.mjs` 可扫描）—— 值得做成定时兜底自动抢救。

## 兜底：定时抢救"打完但没提交成功"的成绩（已上线）

前端不动，全部在服务端做。

### 组件

| 文件 | 作用 |
|---|---|
| `server/recover.js` | `recoverLostRuns(db, now, rule)`：扫描 + 校验 + 写库（纯函数，可单测）|
| `server/recover-cli.js` | 命令行入口，`--dry-run` 走完全一样的代码路径但回滚事务 |
| `deploy/yuanhuo-recover.service` | oneshot，跑一次 CLI |
| `deploy/yuanhuo-recover.timer` | **每 5 分钟**触发（开机 3 分钟后第一次）|

```
sudo systemctl list-timers yuanhuo-recover.timer
sudo systemctl start yuanhuo-recover.service     # 想手动立刻跑一次
journalctl -u yuanhuo-recover -n 50
```

### 写库门槛（比"标记"更严，因为自动写库不可逆）

1. **结束至少 10 分钟**（`minAgeMs`）—— 给客户端正常提交留时间
2. `status === 'over'` 且 `result IS NULL` 且 14 天内
3. 玩家未被封禁、分数 > 0、有 trace
4. `validateRun` **零 flags**（含落点机械/节拍、守恒律、分数上界、秘技上界……）
5. 分数曲线 `score ≤ 1200 + 4×秒` 通过
6. **恢复专用**：每秒得分 ≤ **8**（真人峰值 6.95）。分数曲线带 1200 截距，小局永远合规，
   所以自动写库额外要这条 —— 实测挡下了一局 330 分 / 31 秒（10.78 分/秒）的测试账号记录
7. 幂等：按 `(player_id, mode, score, duration_ms)` 查重；写成功后把 `live_game.result`
   填成 `{ok:true, recovered:true, runId}` —— 这样**客户端事后补交会直接拿到这个结果**
   （不会重复入库，也终于能显示"成绩已保存"），兜底自己也不会重复写
8. 单次最多 50 条（`maxRows`），避免某一小时异常刷榜

任何一条有标记都**不写**，只在日志里留 `跳过 ... ：原因`，转人工。

## 仍然遗留

- 客户端提交失败**没有重试**（要改前端 bundle，本次明确不动）。
  不过现在有了兜底，失败的成绩会在 10 分钟后被自动救回来，玩家下次打开榜单就能看到。
- 提交失败时玩家看到的仍是「已记入本机，暂未进入在线榜单」——这句提示本身没错，只是不知道会有人兜底。
