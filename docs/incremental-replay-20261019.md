# 增量校验（窗口重放）：把"伪造客户端"的成本从 91 秒抬到"必须真跑物理"

> 2026-10-19 上线。涉及 `server/sessions.js`、`server/index.js`。
> 备份目录（服务器）：`/opt/yuanhuo/server/.bak-20261019-1930-sim/`

## 1. 要解决的问题

协议 2 是**客户端权威物理**：客户端只上报一个自洽的 `state`（球阵、分数、合成数、落点轨迹），
服务端不做推演，只做结构检查 + 统计上界。红队实测的完整攻击链是：

```
POST /run/start → 拿到 seed → 本地跑 LCG 预测球序
  → 等到 (n−1)×400ms（真实墙钟）
  → 编一个自洽 state（balls 全空、merges = n−1、score = 10(n−1)）
  → checkpoint → submit
```

拿到经典榜第一只需要 **238 次投放 / 91 秒**。已有的 8 条软规则（落点机械、终局见证、
每次投放得分、存档节奏、终局堆叠自洽、球位置跳变、秘技删除上界、球数/单位守恒）
把"编的"和"真打的"分开了不少，但**凡是只检查"上报数字之间的关系"的规则，
伪造者都能同时编造"，漏网空间始终存在。

增量校验换了一个维度：**相邻两次存档之间的物理演化，服务端自己算一遍**。

## 2. 方案

每次存档（按 12% 抽样）时：

```
prev = 服务端存着的上一次 state        （客户端提供的、已通过结构检查的）
cur  = 客户端这次上报的 state
sim  = Game.restore(prev)              （server/sim/game.js，独立实现）
       → 按 cur.trace 里落在这个窗口内的条目，强制 heldLevel=e.lv、setAimX(62 + e.x*1001)
       → 每次 drop() 后按 1/60 秒步长推到 cur.elapsed
bias = cur.merges − sim.merges         （累计到 live_game.sim_bias）
```

关键点：**落球等级必须用 trace 里的 `lv`**，不能让服务端模拟器自己跑 LCG。
上一版实验漏了这一点，一致率只有 88%，修正后显著变好（见 §3）。

伪造者要么（a）不跑物理 → 编出来的 `merges` 和推演差一个随机游走之外的系统量，
要么（b）真跑物理 → 他上报的分数就是自己选的落点真打出来的分数，**不能再随便编**。
这就是这条规则的全部价值：它不证明客户端诚实，只证明"分数必须来自一次真实的物理演化"。

## 3. 标定（8 个种子，客户端 = web/src/game，服务端 = server/sim，真实帧长抖动）

| 窗口长度 | 窗口数 | 单窗口 σ（客户端−推演） | 均值 | 单窗口耗时 |
|---|---|---|---|---|
| 1.0 秒 | 1008 | 0.480 | +0.029 | 11 ms |
| 1.6 秒 | 610 | 0.871 | +0.011 | 18 ms |
| 2.5 秒 | 386 | 1.332 | −0.039 | 27 ms |

结论：

1. **偏差零均值**——两个独立实现的差异是双向随机噪声，不是系统性偏移，所以可以用随机游走建模。
2. **σ 随窗口长度超线性增长**，所以判据必须按窗口/抽样次数自适应，不能用一个固定比值。
3. 真人单次存档间隔中位数约 1.6 秒 → 实际 σ ≈ 0.87。

一致性（1 秒窗口，用 trace 等级重放）：±0 → 85%，±1 → 97%，±2 → 99%，±3 → 100%。

## 4. 判据

```
真人：累计偏差 ≈ 均值 0、标准差 σ√N 的随机游走
注水者：每窗口偷偷多加 k 次合成 → 累计偏差 ≈ k·N（线性）

判据：|Σbias| > 4 · σ · √N ，且 N ≥ 20
      （σ = 0.9，N = 已抽样窗口数）
```

早期用的是固定比值 `|Σ|/N > 0.5`，问题在**抽样次数少时误报风险升高**（N=10 时 0.5×10=5，
而 σ√10 = 2.8，只是 1.8σ）。改成 4σ√N 之后 N 小的时候界自动收紧，N 大时自动放宽。

边界值：

| N | 4σ√N 界 | 注水 +0.5/窗口 | 注水 +1/窗口 |
|---|---|---|---|
| 20 | 16.1 | 10 ✗ | 20 ✓（勉强）|
| 25 | 18.0 | 12.5 ✗ | 25 ✓ |
| 45 | 24.1 | 22.5 ✗ | 45 ✓ |
| 120 | 39.4 | 60 ✓ | 120 ✓ |
| 200 | 50.9 | 100 ✓ | 200 ✓ |

**验证**：用 Box–Muller 造 20000 局真人规模（N 在 20–200 间随机、每窗口 N(0, 0.9)）
跑判据 → **误报 0/20000**。理论值 p(4σ) ≈ 6.3e-5，20000 局的期望误报 1.3 次，实测 0 次。

注：+0.5/窗口 在短局抓不住是**已知取舍**，不是缺陷——它本身就落在单窗口 ±3 容差内，
且短局注水 0.5×25 ≈ 12 次合成 ≈ 100 分，够不到前二十。

## 5. 抽样参数与 CPU

```js
SIM_RULE = {
  maxWindowMs: 3000,    // 只校验 ≤3 秒的窗口
  minIntervalMs: 1000,  // 同一秒内不重复抽
  sample: 0.12,         // 每次存档 12% 概率抽检
  maxChecks: 200,       // 单局上限
  mergeTolerance: 3,    // 单窗口容差（只用于日志/调试判断）
  sigma: 0.9, sigmaMultiple: 4, minChecks: 20,
}
```

生产对局时长（346 局实测）：p10 = 17 秒、**p50 = 1611 秒（27 分钟）**、p90 = 2949 秒，
≥20 分钟的 222 局。按 1.6 秒一次存档、12% 抽样：

- 27 分钟的对局 → 约 120 次抽样（界 39.4，抓 +0.5/窗口）
- ≥10 分钟的对局 → 约 69 次抽样
- 60–180 秒的对局 → 约 12 次抽样（不到 20，不下结论）

CPU（本机实测，满屏 64 球的最坏窗口 3 秒切片）：p50 59 ms / p90 65 ms。
按 12% 抽样、每位玩家 ≈ 0.6 次存档/秒：**约 0.2% 单核/玩家**，40 名在线玩家同 worker 约 7%。
`maxChecks = 200` 封顶单局成本（≈ 13 秒 CPU 摊在半小时里）。

## 6. 主动跳过的情形（以及为什么不是漏洞）

| 情形 | 原因 |
|---|---|
| `cur.elapsed − prev.elapsed > 3000ms` | σ 随窗口长度超线性增长，长窗口推演不可信 |
| 窗口内用过秘技（`secretCycle − secretCount` 变化） | 秘技删球在 trace 里没有记录，服务端没删 → 必然发散 |
| `prev.status !== 'playing'` | 暂停/结束的窗口没有可比性 |
| trace 条目触发放球冷却（`drop()` 返回 false） | 机制上推演不了，跳过而不是判可疑 |
| `N < 20` | 统计上说明不了任何事 |

**为什么故意拉长存档间隔来躲这条没有用**：存档节奏规则要求真人每分钟 ≥20 次存档
（≤3 秒一次），想躲开 3 秒窗口就得把间隔拉到 3 秒以上，直接撞节奏规则。

## 8. 顺带修掉的缺陷：flag 文本被同类条目挤爆

`live_game.flags` 封顶 500 字符，而 `球数守恒 X > Y（投放…、合成…）` 这类带数字的条目
一次对局能刷出几十条**不同文本**（`Set` 去重对它们无效）。实测一次注水对局里，
球数守恒把 500 字符吃满，**后面才追加的「物理推演不一致」被整条截掉**——
最关键的原因反而在后台看不到。

修法：`mergeFlags()` 按类别（取第一个空格/冒号/括号之前的部分）限量，
每个类别最多留 2 条（第一条 = 什么时候开始不对，最后一条 = 最后有多严重）。

## 10. 后续补强：时间挤压 + 分数增长曲线（2026-10-19 第二轮）

第一版上线后用户提了一个关键质疑：**"193 秒登顶这显然不可能，直接校验时间就完事了"**。
这个判断是对的，而且是更强的第一道闸。核对客户端源码（`web/src/main.ts`）后确认：

| 事实 | 含义 |
|---|---|
| `if (timestamp - lastSave >= 2000) saveProgress()` | 真人每 **2 秒**必定存档一次 |
| `visibilitychange` → `pause()`；物理只在 `!document.hidden` 时推进 | 切后台是**暂停**，`elapsed` 冻结，攒不出大跳变 |
| `networkBusy` / 模态 / 发现动画期间既不同步也不推进 | `elapsed` 不可能跑在存档前面 |

于是攻击者被三面夹住：

- **少存档**（躲开 3 秒重放窗口）→ 节奏规则（<20 次/分）标记。这正是"一次性伪造"的死法。
- **压缩时间**（想快速登顶）→ 483 次投放 × 400ms 冷却 ≥ 193 秒，且 `elapsed ≤ now − started_at + 1500` 卡死。
- **拉开长时间**（想慢慢来）→ 见下面的分数增长曲线。

### 10.1 分数增长曲线（新规则 `SCORE_CURVE`）

```
分数 ≤ 1200 + 4 × 秒
```

等价于 `速率 ≤ 4 + 1200/T 分/秒` —— 正好是"速率随对局变长而衰减"的真实形状。

标定（生产库 **289 局真人**，`score` 与 `duration_ms` 都是服务端校验过的字段）：

| | classic | endless |
|---|---|---|
| 峰值每秒得分 | 6.95（165 秒那局） | 6.87 |
| 中位 | 1.49 | 1.57 |
| 40 分钟以上长局 | 1.79 | 2.96 |

结果：

- **真人 0 误杀**，离曲线最近的一局用到 **72%** 额度（1677 分 / 286 秒）
- 历史 53 条可疑记录里额外抓到 **9 条**（含两个 19999 分 = 38 分/秒、999999 分 = 71088 分/秒）
- **193 秒最多只能报 1972 分**（真机峰值 6.95 分/秒也只够 1341 分）

### 10.2 两条规则怎么互锁

```
想报 5786 分（当前经典榜首）
   → 分数曲线要求 ≥ 19.1 分钟
   → 19 分钟里按真人节奏至少要 579 次存档
   → 物理校验在前 1 分钟内就抽满 20 次（见下面的预热）
   → 伪造的状态序列在 ~60 秒处就会被抓住
```

想报 18454 分（无尽榜首）则要求 ≥ 71.9 分钟。**"编一个自洽的 state"这条路被时间成本封死了。**

### 10.3 预热：前 20 次无条件校验

只靠 12% 抽样时，193 秒的攻击期望只有 `64 × 0.12 ≈ 7.7` 次抽样，永远到不了 20 次门槛。
改成**前 20 次无条件校验**后，"N ≥ 20"从"碰运气"变成"任何对局必然满足"，
代价约 0.4 秒 CPU/局（20 × 20ms），且只在每局开头发生一次。

### 10.4 没有采纳的方案：冷却冲突时延后投放

400ms 极限连点会让 65% 的窗口因投放冷却冲突变成"不可推演"（实测 17/26）。
试过"往后挪几步再投"来把覆盖率提到 100%，但实测 σ 从 0.871 涨到 0.915
（2.5 秒窗口 1.33 → 1.54），单窗口最大偏差从 6 涨到 10 —— **判据灵敏度是靠 σ 撑起来的，
不能为覆盖率让步**。而且连点本身会被分数曲线按住（2.5 次投放/秒 × 12 分 = 30 分/秒）。
所以维持"冲突就跳过"。

## 11. 已知局限（要诚实说清楚）

1. **不能证明客户端真跑了物理**，只能证明"上报的合成数与一次服务端重放的结果在统计上一致"。
   真跑物理 + 精心挑选落点的作弊者依然存在——但那已经不叫伪造，叫"用脚本玩得好"，
   归落点机械/节奏规则管。
2. σ = 0.9 是**播种自动对局**的估计，不是真人样本。真人打法更规整，σ 理应更小
   （误差只会往安全方向偏）；但仍需上线后用真实数据复核。
3. ±0.25 次/窗口以下的微量注水（一局 120 次抽样 → 30 次合成 ≈ 250 分）抓不住。
4. 秘技窗口全部跳过——如果以后秘技变成主流玩法，需要把秘技落点也写进 trace 才能覆盖。
5. **分数曲线是"经验包络"不是物理定律**：真人越练越快，将来一定有人顶到曲线上沿。
   届时按 `tools/verify-score-curve.mjs` 重跑一遍标定再放宽容差，
   不要直接改成"真人打不到"这种拍脑袋的说法。
6. 分数曲线只约束**最终/当前分数**和时长。如果伪造者把分数压在曲线下方（比如 19 分钟报 5700 分，
   速率 5 分/秒 —— 曲线允许），时间这条就只管到"成本"，仍需物理校验兜底。

### 13.1 审计发现

1. **305 局"干净"记录里，只有 2 局会被当前规则标记** —— 都是 `测试脚本` 的

2. **63 局带"同 IP"疑点**，逐个查完全是自聚类：这些账号与自己某一局被标记的记录同 IP，
   或者是校园网 NAT。对高分账号做了打法指纹核对（间隔中位 1.6–3.2 秒、众数占比 1–6%、
   分数/合成 4.2–5.1、落点 66–277 种）——**都符合真人**。
3. **抓到 1 个真漏网：`#84`（1677 分 / 无尽）** —— 见下。

### 13.2 漏网原因：节奏判据被我自己关掉了

第一版 `detectAutomatedDrops` 是「落点机械 **AND** 节奏机械」，导致"延迟随机化"的脚本漏网；
修成 aim-only 之后，反面又漏了"**落点随机 + 节拍精确**"这一类。`#84` 就是这一类：

```
461 次投放，间隔直方图：617ms×304  616ms×152  其余 5 个（99% 挤在 616/617）
落点：277 种、跨度 908px（随机化过，落点判据完全抓不到）
分数：1677，挂在无尽榜上
```

改成 **OR**：落点机械 **或** 节拍机械，任一成立即标记。

阈值标定（285 局干净对局，间隔按 10ms 分桶取众数占比）：

| 分位 | 众数占比 |
|---|---|
| p50 | 2% |
| p90 | 9% |
| p99 | 28% |
| **#84** | **99%** |

`占比 ≥ 50% 且众数 ≥ 600ms` → 干净局**只命中 #84 一局**（与第二名隔 3.5 倍），
已标记局 41 局里命中 10 局，两种脚本形态同时覆盖。

`600ms` 下限是必须的：线上有十几局真人的中位间隔就在 **450–467ms**（顶着 400ms 冷却连点），
这一档在时间维度上与脚本无法区分，所以节拍判据不能往下压。

### 13.3 落点指标的两个混淆（重要，别拿单项当测谎仪）

- **输入方式**：手机玩家天然只有 43–109 种落点（`玩家I` 85 种，已确认真人；
  `玩家V` 66–88 种），而当前判据的下限是 30 种 —— 阈值必须留在这个量级，
  用"真人最少 158 种"当硬阈值会误杀所有手机玩家。

## 14. 事故：自动投放判据曾在"半截 trace"上下结论（2026-10-19 深夜）

### 14.1 现象

部署 OR 判据后 10 分钟内，线上连标 3 局：

| 记录 | 分数 | 最终 trace | 被标记时的说法 |
|---|---|---|---|
| #412 | 980 | 289 次投放 / **35** 个落点 | 「落点只有 27 个固定位置」|
| #414 | 7297 | 1647 次投放 / **647** 个落点 | 「落点只有 29 个固定位置」|
| #416 | 1907 | 532 次投放 / **36** 个落点 | 「落点只有 30 个固定位置」|

#414 尤其荒谬：最终 trace 有 **647 个落点**（x 值 `0.0300, 0.0307, 0.0317…` 连续 1px 递增，
真人鼠标平滑移动），却被判成"只有 29 个固定位置"。

### 14.2 根因

`detectAutomatedDrops` 的阈值（`maxPositions: 30`、落点跨度、节拍占比）全部按**完整 trace**
标定 —— 真人一整局最少 158 种落点。但它是挂在 `checkpoint.js` 上的，**每次存档都跑一次**，
拿到的是"到目前为止"的半截 trace。

实测真人前缀的落点种类：

| 已投次数 | 真人最少落点 | 中位 |
|---|---|---|
| 60–80 | **4** | 53 |
| 80–120 | **4** | 69 |
| 120–200 | **5** | 100 |
| 200–300 | **13** | 158 |
| 300–500 | 39 | 227 |
| 500–1000 | 74 | 361 |
| 1000+ | 272 | 522 |

开局阶段真人的落点就是会很少（一直在一小块区域打），拿完整 trace 的阈值去套，**必然误伤**。
判据本身没错，是我把它放错了位置。

### 14.3 修法（按用户的意见：结束的时候判一次就行）

- 把自动投放判定从 `checkpoint.js` **移到** `validate.js` 的 `validateRun`（提交时、trace 完整、标定成立）
- `checkpoint.js` 只保留"投放间隔 <390ms"这类**逐帧可比**的检查
- 清掉 3 条误标（清前逐条用新的结束判定复核，确认不会再被判）

### 14.4 验证

用新流程重判全库 365 局：

- 305 局干净记录 → **0 误报**
- 58 局已标记记录 → **35 局在结束判定下同样被确认**（蓝鱼 19999、测试账号 2000–7056 全系列），
  其余是靠守恒/跳变/节奏/分数上界这些"中途可比"的维度抓住的，不受影响

### 14.5 遗留（已按用户意见补掉）

`#416`（532 次投放只有 36 个落点）在**全局阈值 30** 下判不了，但同长度真人最少 74 —— 大概率是脚本。
补法：把落点上限做成**随投放数阶梯上升**（`positionCap()`）。

再验一次真人前缀的最小**跨度**，发现窄带判据（`span < 40px`）也有同样的问题：

| 前缀长度 | 真人最小跨度 |
|---|---|
| 60–200 次 | **30px**（玩家I）|
| 300 次 | 80px |
| 500 次 | 892px |

所以窄带判据也必须受"≥300 次投放"这道门槛约束，否则会把朋友判成脚本。

最终阶梯（每一档都取在真人实测下限之下）：

| 已投次数 | 落点上限 | 同长度真人最少 |
|---|---|---|
| < 300 | 不判 | 4–13 种 |
| 300–500 | 30 | 39 种 |
| 500–1000 | 45 | 74 种 |
| ≥ 1000 | 100 | 272 种 |

全库比对（旧固定阈值 → 新阶梯）：

- 干净局：0 命中 → **1 命中（#416）**
- 已标记局被结束判定确认：35 → 28（窄带分支受长度门槛约束后，7 局样本不足 300 次的记录不再由它确认；
  它们本来就已被守恒/分数上界等规则标记，不影响处置）
- `#416` 已按新规则追认标记（`flag_reason` 带「阶梯阈值判定」前缀）

### 14.6 为什么节拍判据不需要长度阶梯

因为它在**任意前缀长度**上都安全 —— 284 局干净记录在 60/100/150/200/300/500 各档命中 0 局，
最高众数占比 34%（阈值 50%）；已标记局即使在 60 前缀上也有 11/42 命中。
落点判据之所以需要阶梯，是因为"落点种类"这个量会**随对局长度单调增长**，节拍占比不会。
